# x402.rs Facilitator: Lessons Learned

## Overview

This document details the challenges encountered when implementing x402 payments with the public `facilitator.x402.rs` instance, and why we ultimately switched to PayAI's facilitator for production use.

## The Problem

The public x402.rs facilitator at `https://facilitator.x402.rs` **can verify payments but cannot settle them on Base mainnet**.

### What Worked

- `/verify` endpoint correctly validates EIP-3009 `transferWithAuthorization` signatures
- Returns `isValid: true` for properly signed payment payloads
- Supports Base mainnet network identifier (`base` for V1)

### What Failed

Settlement requests return:
```json
{"error": "Invalid request"}
```

This happens because the public x402.rs instance **does not have funded signer wallets** to pay gas for submitting transactions on Base mainnet.

## Technical Details

### How x402 Settlement Actually Works

1. Client signs an EIP-3009 `transferWithAuthorization` for USDC
2. This signature authorizes anyone to submit the transfer on the client's behalf
3. The facilitator receives this signature and calls USDC's `transferWithAuthorization` function
4. **The facilitator pays ETH gas** to submit the transaction (as `msg.sender`)
5. The USDC moves from buyer to recipient

> **Key insight:** Facilitators like PayAI subsidize gas costs. They pay ~$0.001 in ETH per transaction to submit the buyer's signed authorization on-chain.

### Why x402.rs Public Facilitator Can't Settle

The public demo instance at `facilitator.x402.rs`:
- Has verification logic enabled for all networks
- Does NOT have funded signer wallets for mainnet settlement
- Settlement requires ETH for gas - public instance lacks this
- Intended for testing/demo purposes, not production

### Proof: Checking Supported Networks

```bash
curl -s "https://facilitator.x402.rs/supported"
```

Returns `base` as supported, but `/supported` only indicates **verification** capability, not **settlement** capability.

## Version Compatibility Issues

### V1 vs V2 Protocol

x402.rs only supports **V1** of the protocol:

| Feature | V1 | V2 |
|---------|----|----|
| Network format | Simple (`base`) | CAIP-2 (`eip155:8453`) |
| Amount field | `maxAmountRequired` | `amount` |
| Resource location | Inside `accepts[]` | Top-level `resource` object |
| SDK class | `ExactEvmSchemeV1` | `ExactEvmScheme` |
| Registration | `registerV1("base", ...)` | `register("eip155:8453", ...)` |

### Error Messages Encountered

1. **"Unsupported x402Version: 2"**
   - Cause: Sending V2 format to V1-only facilitator
   - Fix: Use `x402Version: 1` in PaymentRequired response

2. **"unknown variant `eip155:8453`"**
   - Cause: Using CAIP-2 network format with V1
   - Fix: Use simple network name `base`

3. **"Cannot convert undefined to a BigInt"**
   - Cause: Using V2 SDK classes with V1 requirements
   - Fix: Import from `@x402/evm/v1` and use `ExactEvmSchemeV1`

4. **"missing field `x402Version` at line 1 column 918"**
   - Cause: Request body missing `x402Version` at top level
   - Fix: Include `x402Version: 1` in verify/settle request body

## Recommendations

### For Production

Use **PayAI** (`https://facilitator.payai.network`):
- No API key required
- Has funded signers for Base mainnet (subsidizes gas costs)
- Supports both V1 and V2 protocols
- Actually settles transactions on-chain

### For Self-Hosting

If you want to run your own x402.rs facilitator:
1. Deploy the x402-rs binary
2. Configure a private key with ETH for gas
3. Set up RPC endpoints for your target networks
4. Ensure the signer has sufficient ETH balance

### For Testing

- Use `base-sepolia` testnet with x402.rs
- x402.rs may have funded testnet signers
- Get testnet ETH and USDC from faucets
